# Update — Change in Direction (v2)

This supersedes the previous version of this document, which described a white-label, self-hosted plan. Read this alongside `README.md` and `BUILD_PLAN.md`.

## Summary

This project has gone through three shapes:

1. **Hackathon standalone app** ("Cue"), built for Wema Bank Hackaholics 2026, with its own signup, login, and branding.
2. **White-label**, where each bank deploys its own copy on its own infrastructure. This was chosen and partly built, then reversed.
3. **Current: one hosted, multi-tenant platform.** Banks integrate through an API key generated by Cue rather than deploying their own copy.

The core problem and solution remain the same. Customers wait too long in bank branches for services that could be handled faster or remotely. What changed is who runs the software and how a bank connects to it.

## Current Architecture

**Multi-tenant by design.** Every bank is identified by `bank` on `Admin` and `Branch`, and by `bankName` on `ApiKey`. One deployment serves multiple banks. `bankScope` filters downstream queries to the requesting bank's branches, and `tenantMatch` prevents a bank admin from combining their JWT session with another bank's API key.

**Two API surfaces:**

- **Public, no API key required:**
  - `GET /api/v1/queues`
  - `POST /api/v1/tickets`
  - `GET /api/v1/tickets/public/:id`
  - `PATCH /api/v1/tickets/:id/cancel`
- **Authenticated, API key required:** branch listings, staff actions such as call-next/complete/skip, analytics, and administrative operations. These endpoints are permission-scoped and rate-limited per key.

The public guest ticket flow is mounted before the authenticated v1 router, so customers never need to hold an API key. Bank integrations call these same public paths from their own customer-facing applications.

**API key lifecycle:** a bank admin requests a key, a platform superadmin reviews and approves it, the raw key is AES-256-GCM encrypted for a one-time bank-admin reveal, and the raw key is never stored in plaintext. Keys support scopes, expiry, suspension, revocation, and rotation with a grace period.

**Internal operations console:** staff, manager, bank admin, and superadmin dashboards are Cue's own JWT-authenticated UI. This is the product UI Cue serves. It uses one consistent Cue identity across banks, similar to a vendor-operated SaaS console.

**Branding:** intentionally one global identity rather than per-bank branding. Production customers use the bank's own application, so there is no customer-facing Cue interface to brand per tenant.

**Customer-facing React frontend:** a demo and integration proof-of-concept, not the production customer surface. Real bank integrations build their own ticket UI against the public `/api/v1` endpoints.

## What's Already Built

- Full role split: `Admin`, `Manager`, `Staff`, and `Superadmin`, each with its own model and JWT auth path
- Tenant isolation through `bankScope`, `tenantMatch`, and branch ownership checks
- API key model with bcrypt-hashed storage, scopes, rate limits, expiry, suspension, revocation, and rotation
- Request-and-approve key issuance with encrypted one-time reveal
- Public guest ticket flow backed by `/api/v1/*`
- JWT-only internal dashboard with role-specific views
- Integration snippets and a full in-app integration guide for bank admins
- API-key test connection endpoint for validating a key before deploying it
- Swagger UI mounted at `/api/docs`
- 137 backend tests across 17 test files and 8 frontend tests
- Groq-based AI agent preserved in `deferred/`; it is not part of the current production flow

## Phase 1 — Point the Demo at the Public API

The demo's guest queue and ticket flow now calls the public v1 API directly. No relay, proxy, or API key is used.

Updated guest operations:

- `GET /api/v1/queues`
- `POST /api/v1/tickets`
- `GET /api/v1/tickets/public/:id`
- `PATCH /api/v1/tickets/:id/cancel`

The dashboard and staff operations remain JWT-authenticated on `/api/*` or the appropriate internal routes. They were not moved to the public guest flow.

## Phase 2 — Consolidate Guest Appointments Under v1

Appointments still use the legacy guest routes outside the v1 surface. This is functional but leaves two public conventions.

The optional cleanup is to add the following routes to `backend/src/routes/v1/public.routes.js`:

```js
publicRouter.get(
  "/appointments/slots",
  getSlotsValidator,
  validate,
  getAvailableSlots,
);
publicRouter.post(
  "/appointments",
  createAppointmentValidator,
  validate,
  createAppointment,
);
publicRouter.get(
  "/appointments/:kioskId",
  appointmentIdParamValidator,
  validate,
  getAppointmentTicket,
);
```

The current appointment flow should continue working while this remains optional.

## Phase 3 — Integration Documentation for Banks

The bank-admin integration surface now includes:

- Copy-paste examples for cURL, JavaScript, Python, and Node
- Integration snippets during the one-time key reveal
- Expandable snippets for approved keys in the request list
- Key test connection from the dashboard
- Admin-only `/integration` guide covering authentication, scopes, rate limits, bank scoping, key lifecycle, errors, sample workflows, Swagger, and Postman/Hoppscotch usage
- Swagger UI at `/api/docs`

The remaining documentation work is to bring the full OpenAPI specification up to date with the current v1, dashboard, and platform routes.

## Phase 4 — AI Service Advisor (Deferred)

The AI Service Advisor remains the intended differentiator but is deferred until the integration story is solid.

Planned design:

- `ServiceMatrix` collection mapping services to rules
- `check-service` endpoint
- Override tracking on tickets
- Admin-facing deflection metrics and estimated cost savings

## Current Direction

Cue is now a hosted, multi-tenant queue integration service. The bank's backend or customer-facing application uses Cue's public guest API for ticket creation and tracking, while Cue's staff and operations users use the internal JWT dashboard. The bank admin receives and manages scoped API keys through Cue's own admin console.
